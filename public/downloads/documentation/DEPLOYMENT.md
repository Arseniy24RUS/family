# Публикация, запуск и обновление

## GitHub Pages через Actions

Создайте репозиторий с основной веткой `main`. Скопируйте содержимое каталога проекта в корень репозитория. Папки `.github`, `src`, `public`, `scripts`, `tests`, `documentation` и готовая `docs` должны находиться рядом с `package.json`, а не внутри дополнительного каталога.

Для загрузки большого комплекта файлов можно использовать GitHub Desktop: клонировать пустой репозиторий, скопировать файлы в локальную папку, выполнить commit и Push origin. Другая возможность — обычный Git. Доступ к вашему аккаунту или создание репозитория не выполнялись при подготовке ZIP.

В Settings → Pages выберите Source → GitHub Actions. Workflow **Deploy research platform** запускается после push в `main`/`master` или вручную. Он проверяет JavaScript, создаёт `docs`, сверяет файлы, загружает Pages-артефакт и отдельно развёртывает его. Задание deployment зависит от успешного build.

Нужны разрешения `pages: write` и `id-token: write` у deployment. Для записи результатов ЕМИСС нужны `contents: write` у refresh. Они заданы в YAML по отдельным заданиям. Настройки организации или protected branch могут запрещать запись даже при наличии этих строк. В таком случае требуется разрешить предусмотренный бот-коммит либо адаптировать workflow к pull request. Принудительная запись и обход правил защиты не применяются.

После первого открытия проверьте страницу «Обновление ЕМИСС». Исходное состояние `not_yet_fetched` ожидаемо: сайт уже доступен, запросы ещё не выполнялись.

## Первый запрос к ЕМИСС

На вкладке Actions откройте **Refresh EMISS and deploy** и нажмите Run workflow. Для короткой проверки введите `data_21`; после её проверки запустите без параметра. Итоговая сводка содержит статус каждого источника. Состояние workflow «success» означает, что процесс диагностики и публикации завершился; факт успешной загрузки источников определяется по строкам отчёта, а не по зелёному значку workflow.

По умолчанию скрипт публикует диагностику даже при недоступности всех источников и сохраняет предыдущие значения. Такое поведение позволяет показать посетителю причину сбоя. В ручном локальном запуске `--strict` возвращает код 2 при неполном/неудачном обновлении.

## Ежемесячный цикл

Расписание: `23 4 8 * *`, UTC. Меняется в `.github/workflows/refresh-emiss.yml`. Это частота проверки платформы. Сроки публикации у отдельных статистических показателей могут различаться.

Workflow работает на основной ветке. GitHub предупреждает, что расписание может задерживаться, а в публичном репозитории отключается после 60 дней отсутствия активности. Проверяйте вкладку Actions; ручной запуск предусмотрен независимо от даты. Источник: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows

После обновления данные и диагностика записываются только в `public/data/latest/`, коммитятся ботом, затем в том же workflow собирается и публикуется сайт. Не предполагается, что push с `GITHUB_TOKEN` обязательно запустит другой workflow. При конфликте ветки нет принудительного push: ошибка видна в Actions.

## Альтернатива без вычислительного workflow

Готовую `docs/` можно опубликовать через Settings → Pages → Deploy from a branch → main → /docs. Архивные страницы сразу работают. Однако в такой конфигурации автоматический цикл Actions-публикации нужно отдельно согласовать с выбранным источником Pages; для штатного автоматического обновления используйте GitHub Actions. Простое размещение ZIP на странице GitHub не запускает сайт.

## Работа на локальном компьютере

Для показа готовой версии запустите `python -m http.server 8080 --directory docs`. Для изменения интерфейса редактируйте `src`, затем выполняйте `npm run build`. Название репозитория, персональный домен и абсолютный путь не зашиты в исходный код. Маршруты вида `#/map?source=data_21&r=77` работают без серверного перенаправления.

Отдельно после реального размещения проверьте на внешнем устройстве открытие глубокой ссылки, скачивание PDF/ZIP, Blob Worker в лаборатории и страницу обновления. Эти проверки не заменяются локальными тестами.

Официальные документы: https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages и https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow
